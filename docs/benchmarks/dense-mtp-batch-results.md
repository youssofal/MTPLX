# Dense batched MTP - concurrency benchmark results

Measured on stock MLX (no MLX source changes; the verify kernel is built
through the public `mx.fast.metal_kernel` JIT interface).

Every arm is fixed-length: `--ignore-stop` makes each stream generate
exactly `--max-new` tokens, so `gen` is always n x 512 and aggregate
throughput is comparable across concurrency levels. Without it, streams
hit EOS at different points and finished rows still cost full batch width
per cycle, so the aggregate curve would measure stop-timing, not speed.

## Setup

| | |
|---|---|
| Hardware | Apple M3 Ultra, 256 GB unified memory |
| MLX | 0.32.1 (stock, from PyPI) |
| Models | ref-Qwen3.8-27B-MTPLX-Optimized-Speed and grant-ai/Qwen3.8-27B-Abliterated-MTPLX-4bit, both 4-bit |
| MTP | depth 3 (3 drafted + 1 verified per cycle) |
| Prompt | bundled suite `mtplx/benchmarks/prompts/long_code.jsonl` |
| Tokens | 512 per stream, fixed |
| Driver | `generate_dense_mtp_batch`, pipelined loop, committed head history, kvshared ragged attention |

```
python -m mtplx.benchmarks.runners.dense_batch_bench \
    --model <model> --prompt-file <suite prompt> \
    --batches 1,2,4,6,8,10,12,16,24,32 --depths 3 --max-new 512 \
    --vary-suffix --ignore-stop --ragged-2pass \
    --head-history committed --capture-backend linear-gdn-from-conv-stream \
    --loop-mode pipelined \
    [--thinking off | --thinking on --reasoning-effort low|medium|xhigh] \
    [--temperature 1.0 --top-p 0.95 --top-k 20 --sampling-seed 1234]
```

### Known limitation of these runs

The bundled `long_code` task finishes naturally in roughly 64-400 tokens,
but `--ignore-stop` holds every stream open to 512. Tokens generated
after a stream would have stopped are continuation filler, and filler is
unusually easy for the draft head to predict - one arm below reaches
0.99 acceptance at all three depths, which is a repetition loop rather
than a real result. Consequences:

* Reported ACCEPTANCE (and therefore tau) is optimistic relative to a
  workload whose answers genuinely run to 512 tokens. The distortion is
  worst at n = 1-2, where a single looping stream dominates the cohort,
  and dilutes as n grows because `--vary-suffix` gives each row a
  different continuation.
* Reported THROUGHPUT is a real measurement of the machinery either way,
  and the tile-band findings, reproducibility checks, and cross-model
  comparisons are unaffected, since every arm shares this discipline.
* Because the d% columns are computed against n = 1, an inflated n = 1
  baseline UNDERSTATES the scaling factors reported here.

Headline numbers measured on a task whose natural output exceeds 512
tokens are reported separately where available.

`tau/cyc` is tokens committed per cycle across the cohort; `tau/stream`
divides that by n (ceiling 4.0 at depth 3). Non-zero acceptance at every
depth on every arm confirms the MTP head drafts throughout.

## Abliterated: grant-ai/Qwen3.8-27B-Abliterated-MTPLX-4bit

Same driver, prompts, and fixed-length discipline. 4-bit group-64 trunk
with a 5-bit group-64 MTP head, carrying a LoRA-tuned head. It is
included because it exercises the lane on weights this project did not
produce: the batching machinery, the ragged per-row accept path, and the
verify-matmul band behaviour all reproduce on it. Absolute throughput
differs because the trunk quantization and the head differ, so the two
models are not a controlled comparison of any single variable.

## Correctness gate

Parity was run on Optimized-Speed at four cohort sizes. Every
stream decoded in a cohort was byte-identical to the same stream decoded
alone inside a same-size cohort padded with dummy rows, so kernel shapes
match and a mismatch could only mean cross-row contamination.

| cohort size | parity | mismatched streams |
|---|---|---|
| 2 | PASS | 0 |
| 4 | PASS | 0 |
| 8 | PASS | 0 |
| 16 | PASS | 0 |

Abliterated passes the same gate at cohort sizes 2 and 4 on 24k
prompts, on the rebased base and again on the final branch.

## Reproducibility check

Cells with outlying acceptance were rerun with identical settings and
the same sampling seed.

| cell | n | rerun agg tok/s | rerun accept d1/d2/d3 |
|---|---|---|---|
| prod-medium | 6 | 104.18 | 0.830/0.654/0.480 |
| prod-medium | 8 | 125.82 | 0.798/0.582/0.404 |
| prod-xhigh | 2 | 73.64 | 0.781/0.575/0.385 |
| prod-xhigh | 6 | 100.16 | 0.804/0.570/0.402 |
| prod-xhigh | 8 | 122.43 | 0.809/0.630/0.465 |
| t0-medium | 10 | 104.30 | 0.818/0.634/0.487 |
| t0-xhigh | 10 | 98.23 | 0.775/0.574/0.408 |
| t0-xhigh | 12 | 109.29 | 0.783/0.581/0.421 |

Every rerun matched its original within +/-0.15% on throughput with
bit-identical acceptance vectors, on both the greedy and sampled paths.

Two cells that break the pattern of their neighbours were rerun
separately and both reproduced, so they are reported as measured:

| cell | n | original | rerun |
|---|---|---|---|
| Abliterated, temperature 0, medium | 16 / 24 / 32 | 181.83 / 157.26 / 161.11 | 181.88 / 157.42 / 161.11 |
| Optimized-Speed, temperature 1.0, medium | 24 / 32 | 193.91 / 120.29 | 193.87 / 120.15 |

In the second case the cohort commits fewer tokens per cycle at 32
streams than at 24 (54.25 against 68.27) while acceptance stays healthy,
so the loss is cycle cost rather than draft quality. The cause is not yet
identified.

## Observations

* Aggregate throughput peaks where `n x (depth+1)` lands on a 32-row
  matmul band boundary (n = 8, 16, 24, 32); n = 10 and 12 straddle a band
  and dip by 20-25%. The pattern reproduces across reasoning levels, both
  sampling settings, and both models, so it is a property of the
  verify matmul rather than of draft quality. Deployments should size
  cohorts so that `n x (depth+1)` is a multiple of 32.
* Greedy decoding keeps scaling to n = 32. Sampled decoding is lower and
  less regular, with larger local dips, but most levels still gain from
  n = 16 to n = 32.
* Exactness-preserving speculative sampling costs 4-8% versus greedy at
  moderate concurrency, more at the ceiling.
