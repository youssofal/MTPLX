# MTPLX 2.13.2

MTPLX 2.13.2 keeps Inkling 2 Mini on its fast decoder when a client sets top-p or top-k, so those requests now run more than twice as fast as on 2.13.1. It also fixes three bugs that broke real sessions: parallel tool calls merging into one in a streamed reply, memory refusals on 24 GB Macs, and an HTTP 500 after a saved conversation was restored. Your downloaded packs keep working as they are.

Measured on an M5 Max MacBook Pro (128 GB), against 2.13.1.

| What you do | 2.13.1 | 2.13.2 | Change |
|---|---|---|---:|
| Generate a 256-token answer on Inkling 2 Mini Bare Speed with top-p 0.95, after a 558-token prompt | 34.76 tok/s | 81.67 tok/s | +135.0% |
| Ask Pi, OpenCode or Hermes to read two files in one turn, on Optimized Speed | 0 of 3 clients ran both reads from the first reply | 3 of 3 clients ran both reads from the first reply | Fixed |
| Stream a reply that holds two or three tool calls | 0 of 8 replays delivered every call on its own | 8 of 8 replays delivered every call on its own | Fixed |
| Send a 4K prompt after a short request on Bare Speed, on a simulated 24 GB Mac with 4.5 GiB used by other apps | Refused with a memory error after the stream had opened | Answered in full, 400 tokens | Fixed |
| Send a follow-up after the server restores a saved Inkling 2 Mini conversation from disk (#710) | 2 of 2 follow-ups failed with HTTP 500 | 2 of 2 follow-ups completed, and the greedy one matched a fresh run in all 128 tokens | Fixed |

The top-p row is the mean of two runs on each version, taken across four server starts that alternated between the two versions, with every run at nominal thermal pressure. The 2.13.2 client runs used Pi 1.6.0, OpenCode 1.19.6 and Hermes 0.21.6. The 24 GB row ran on the 128 GB Mac set to behave like a 24 GB one.

## Speed

- **Top-p and top-k no longer slow Inkling 2 Mini down.** In 2.13.1, a request that set top-p or top-k left the fast decoder and chose every token on the slower CPU path, so on Bare Speed it ran 63.9% slower than the same request at the model's own sampler. 2.13.2 applies top-p and top-k on the GPU before it decides which drafted tokens to keep, and the gap is now 13.7%.

- **The gain holds at every prompt length we tried.** On an earlier 2.13.2 test build, top-p 0.95 on Bare Speed went from 33.9 to 80.2 tok/s after a 4,142-token prompt and from 33.3 to 91.4 tok/s after a 16,430-token prompt. On Optimized Speed it went from 34.1 to 75.7 tok/s after 558 tokens, from 33.1 to 79.1 after 4,142 and from 33.2 to 79.8 after 16,430. Each figure is the mean of two runs.

- **Every Inkling 2 Mini pack takes the fast path.** With top-p 0.95 or top-k 40, 12 of 12 test requests across the six packs ran every round on the GPU, including the three FP16 builds on the code path that M1 and M2 Macs take, simulated on the M5 Max.

## Draft depth on Inkling 2 Mini

- **Inkling 2 Mini now drafts 3 tokens per round by default.** When a request does not set a draft depth, 2.13.2 drafts three tokens each round instead of choosing a depth each round. 2.13.1 made that choice from round costs it measured once at load, and those costs priced longer drafts too low: on Bare Speed after a 4,167-token prompt it expected a fourth draft token to cost 14.0% more time than three, while the rounds it served took 33.8% more. After a long prompt it therefore often drafted four or more tokens and lost time.

- **In one test, a fixed draft of 3 was up to 22% faster on short answers after a long prompt.** This test ran on 2.13.1 with a 4,167-token prompt, the model's own sampler and 256-token answers, comparing the automatic choice with the depth set to 3 by hand. 2.13.2's default gives the same tokens and the same rounds as 2.13.1 set to 3, which we checked on Bare Speed and Optimized Quality. Each figure is the mean of two runs, and each automatic figure includes the first request after the server started, which is slower on either setting.

| Pack, in that test | 2.13.1, depth chosen each round | Depth 3, the 2.13.2 default | Change |
|---|---:|---:|---:|
| Bare Speed | 87.85 tok/s | 107.48 tok/s | +22.3% |
| Optimized Speed | 99.29 tok/s | 121.26 tok/s | +22.1% |
| Optimized Quality | 81.22 tok/s | 96.32 tok/s | +18.6% |

- **On our standard 4,142-token coding prompt, 2.13.2 is about level with 2.13.1.** On Bare Speed with the model's own sampler and 256-token answers, 2.13.1 ran 91.38 tok/s and 2.13.2 ran 86.94 tok/s. The two orders of alternating server starts gave -0.3% and -9.4%, so we read this as level, not as a gain or a loss. Greedy answers ran 82.08 and 83.36 tok/s. After a 558-token prompt, the model's own sampler ran 96.28 and 94.60 tok/s, and greedy ran 89.63 and 95.37.

- **Long answers gain a little.** For 1,500-token answers after the 4,167-token prompt, Bare Speed went from 99.15 to 99.86 tok/s (+0.7%) and Optimized Speed from 96.37 to 101.07 tok/s (+4.9%), the mean of two runs each.

- **You can keep the old behavior.** A draft depth sent by a client, or set at launch with `--depth`, still applies. Setting `MTPLX_INKLING_DEPTH=auto` brings back the choice each round.

- **Greedy answers are identical to 2.13.1, token for token.** With sampling, the model's distribution is unchanged, but the answer for a given seed can differ from 2.13.1.

- **Measured on an M5 Max only.** Macs with an M1 to M4 chip take another code path. One request on that path, simulated on the M5 Max, ran at the new default. Its speed on those chips is not measured.

- Thank you to @Aster-cmd, whose report in #710 led to this change.

## Tool calling

- **Parallel tool calls keep their own arguments in a stream (#709).** Inkling 2 Mini writes each call in its own block, and 2.13.1 numbered every block from zero, so the second call took the first call's index. Clients then received one call whose arguments were two JSON objects joined together. 2.13.2 gives each call its own index on `/v1/chat/completions` and `/v1/messages`.

- **A tool call no longer arrives as plain text.** When the stream chunk that closed one call also held the start of the next, 2.13.1 dropped that start and sent the next call as text. 2.13.2 keeps it.

- **The coding clients finish the turn.** On 2.13.2, Pi, OpenCode and Hermes each ran both file reads from the first reply and answered with the values from both files. On 2.13.1 every first reply joined the two calls; two clients recovered by retrying, and the third ran out of time while retrying.

- **Every streamed case is covered.** The replays sent the same tool twice, two different tools and three calls in one reply, on both endpoints. Replies without streaming were already right on 2.13.1, in 2 of 2 replays, and stay right.

## 24 GB Macs

- **Longer Inkling 2 Mini prompts are served instead of refused.** On a simulated 24 GB Mac with 4.5 GiB used by other apps, 2.13.1 refused a 4K prompt sent after a short request. 2.13.2 answered it in full, and answered a 6K prompt as well. In the same simulation, cold 8K, 16K and 24K prompts that 2.13.1 refused were served by the fix. The memory guard now waits for memory that MLX is still giving back before it decides, and it counts the memory MTPLX can reuse: its own cache, the saved conversations and queued disk writes.

- **A request that cannot fit is refused before its stream opens.** 2.13.1 sent the memory error after the reply had started, which many clients show as a broken stream. Now a request that clearly cannot fit gets a real 507 before the response begins. The check never runs while another request is still finishing, so it does not refuse a request that would have fit.

- **A long prompt is no longer stopped partway through.** A second safety check ignored the memory MTPLX holds for reuse and stopped prompt reads that the memory guard had already admitted, saying the Mac had run out of free memory. In the simulation it stopped a 24K read at chunk 43 of 49, and a 16K read of an FP16 pack on the M1 to M4 code path. It now counts that memory.

- **The image encoder gives its memory back.** After an image turn, the encoder keeps 0.59 GiB in memory. When a text request would otherwise be refused, MTPLX now releases it first, and the next image reads the encoder from disk again. In the simulation, a cold 24K text prompt after an image turn had been refused 0.20 GiB short.

- **Faster prompt reads on 24 to 36 GB Macs.** Prompts of 4K tokens and more now use Inkling 2 Mini's faster prompt attention on these Macs. In the simulation it handled 432 of 432 attention calls at 4K and 576 of 576 at 6K. Because the prompt is read a different way, sampled and greedy answers on these Macs can be worded differently from 2.13.1.

- **16 GB Macs gain too.** On a simulated 16 GB Mac running Bonsai 2 27B Optimized Speed, a 6K prompt that 2.13.1 refused after its stream had opened is now served.

## Saved conversations

- **A restored conversation no longer fails with HTTP 500 (#710).** After the server restarted with an Inkling 2 Mini conversation saved on disk, 2.13.1 could fail the next request with HTTP 500, and the server log said "Visits disagree on the committed length". Sampled and greedy requests both failed. 2.13.2 resumes right after the last saved token. With the reporter's server settings, the restored greedy request returned the same 128 tokens as a fresh run.

- **Restored requests stay on the fast path.** In the reporter's own run on 2.13.1, the same fault sent 45 of 49 decode rounds to a slower path. On 2.13.2, no restored round left the fast path for that reason.

- **Conversations that 2.13.1 saved in that state are read again** from the prompt instead of being restored at the wrong position.

- **If you turned off the SSD session cache to work around this on 2.13.1** (`--ssd-session-cache off`), you can turn it back on.

## Known in this release

- **The 24 GB and 16 GB fixes were tested in simulation only**, on the 128 GB M5 Max. Nobody has run 2.13.2 on a real 24 GB Mac yet. If you have one, an issue with your results helps.

- **Some memory refusals can still arrive after the stream has opened.** 2.13.2 refuses up front only a request that clearly cannot fit; a request that runs short later is still refused inside the stream.

- **The first token after a new prompt is slightly later on Bare Speed.** After a cold 4,142-token prompt it arrives in 1.726 seconds on 2.13.2 against 1.641 seconds on 2.13.1, the mean of four requests on each, in the same alternating test as the top-p row.

- **A top-p round can still move to the CPU** when the GPU cannot confirm which tokens to keep. This happened in 1 of 65 rounds in our image test on 2.13.2.

## Upgrading

The app updates itself (MTPLX menu, Check for Updates). With Homebrew: `brew update && brew upgrade mtplx`. With pip: `pip install -U mtplx`. The packs did not change, so nothing needs to be downloaded again. This release is version 2.13.2, build 2013021.
