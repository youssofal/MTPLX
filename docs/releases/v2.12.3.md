# MTPLX 2.12.3

MTPLX 2.12.3 brings back the prompt cache for Flash-Next in OpenCode and in plain API clients. In 2.12.2 those clients read their whole conversation again on every request, so each turn waited longer for its first token than the one before. This release also fixes an HTTP 500 that stopped Flash-Next turns after a compaction, a restore from the SSD cache that could build an answer on another conversation's saved state, four more SSD cache bugs, a server that stopped answering after about two days on an Ultra, and a set of problems in Claude Code, Codex and OpenCode sessions.

## What changed

### Prompt cache

- **Flash-Next follow-up turns reuse the conversation again** (#591, #616, #649). 2.12.2 saved Flash-Next conversations without the draft head's history whenever it kept no live copy of the conversation, which is what happens for OpenCode's tool turns, for API clients that name no session, and for a turn saved after it ended. The next turn matched the saved conversation, found nothing it could resume from, and read the whole prompt again, reported as a new session. Saved conversations now keep that history, as they did before 2.12.2's one-copy store; the conversation that stays live is still not copied. A turn that finds a saved conversation without its history (one saved by 2.12.2) now says `no_snapshot_coverage` instead of `new_session`.
- **A new conversation about the same document resumes inside the earlier prompt** (#649, #637 by @jvmenen). When the memory guard skipped saving a cold prompt on its own, the restore points recorded while reading it were dropped with the request. The turn's final save now keeps them, so a new conversation that shares the system prompt, the tools or a long document resumes at the nearest point instead of reading everything again.
- **Plain Flash-Next chat with the SSD cache off resumes at the previous turn** (#291). A client that sends the answer back without its reasoning makes the history diverge where the assistant turn starts, so the next turn resumes from the anchor saved at the end of the previous prompt. Without the SSD cache that anchor was saved only for requests with tools, so every chat follow-up resumed at the first turn's prompt and re-read one more answer than the turn before. Flash-Next now saves it for plain chat too, at no copy of the conversation.
- **A retry or regenerate resumes from the saved prompt** (#661 by @a3rosol). Resending the same prompt read it again from the start (23.5 s on a 16,000-token prompt on an M1 Ultra in the report). The saved answer now keeps the prompt's last logits, about 1 MB, so a retry starts decoding at once.
- **Long sessions without a session id keep their cache** (#624). A client that sends no session id on `/v1/chat/completions`, and whose earlier turn MTPLX renders back a little differently from what it generated, lost its session once the conversation grew past about four times the point of that difference. The next turn then restored only an old part of the conversation: 35,440 of 163,242 tokens, and 95.6 s to the first token, in the report. A difference anywhere inside a turn MTPLX generated now keeps the session at any length. A difference inside a message you wrote still starts a new one.
- **`MTPLX_MTP_HISTORY_POLICY=cycle` keeps the prompt cache** (#400, #422). On M1 and M2 Macs, where the default draft history can make each verify step slow (4 to 5 tok/s on an M2 Max in #400), `cycle` is the setting that brings the speed back. With it, every turn read the whole conversation again (166 s to the first token at 76,000 tokens and 292 s at 108,000 on an M2 Ultra, from #422), because the server saved each turn under a different label from the one the next turn looked for. Saved conversations now restore under `cycle` as they do by default. Nothing changes for anyone who does not set it.
- **Plain decoding resumes each conversation from the previous turn.** With `--generation-mode ar`, `--no-mtp`, `--stock-ar` or `--no-load-mtp` on a Qwen model, a follow-up turn resumed from the last turn that added at least 1,024 tokens, so it could read up to about 1,000 tokens of the conversation again. Plain decoding now saves each prompt before it answers, as speculative decoding does, and the next turn resumes there. This matters most on M1 and M2 Macs that switch Flash-Next to plain decoding (#400). 2.12.2 behaved the same.

### Flash-Next and the SSD cache

- **No more HTTP 500 before the first token after a compaction** (#592, #605). A turn that resumed from the start of a longer saved conversation, after a compaction, an edited message or in a new conversation with the same system prompt and tools, failed with `QSA pooled hold N rows; resizing to M would cut them`, and instant retries failed the same way. The attention index carried the longer conversation's block count into the restored turn. The count is now taken from the restored conversation itself (#650 by @goodbadwolf), and a resize keeps only the blocks the conversation covers (adapted from #657 by @transcendence-x). In a replay of #605 through the shipped restore, the turn that raised the error now resizes 122,880 bytes of index buffers and runs on the compiled verifier.
- **No more answers built on another conversation's blocks** (#635). The same inherited count made a restored turn select attention blocks from the longer saved conversation, and every later turn inherited them. In a replay, 25 of 64 new tokens got a different attention output; a restored turn now decodes the same tokens and final logits as a cold start.
- **One cost of that fix, paid once.** Flash-Next conversations saved to the SSD cache by 2.11.2 to 2.12.2 may hold another conversation's blocks, and nothing in a saved entry says which, so they are no longer used. The first turn of each such conversation after updating reads its prompt once (about 92 s for a 65,000-token prompt on an M3 Ultra, from #635). The cache's normal eviction reclaims the old entries; nothing is deleted or moved by hand. Other models keep their saved conversations.
- **A conversation restored from the SSD cache runs on the layout its request asked for** (#608 by @jvmenen, the same fix in #668 by @CocoaBeans). It ran paged, so its first token and its whole answer were slower than a restore from memory. Measured by @CocoaBeans on an M5 Pro with 64 GB and Qwen 3.8 27B Optimized Speed, a 62,000-token exact restore: prompt 50.1 to 303.2 tok/s, decode 15.0 to 23.7 tok/s, first token 124.7 to 23.4 s.
- **A conversation moved to the SSD cache restores its own state** (#609 by @jvmenen). When another conversation with the same system prompt stayed in memory, the moved one restored only that system prompt (143 to 146 s at 50,000 tokens in the report, or a 507) and held a decoded 5.4 GB copy through its prompt. It now restores its own entry (about 4 s in the contributor's run), and candidates it does not use are released before the prompt is read.
- **A partial restore from the SSD cache works on paged and tail-owned caches** (#655, fixed in #656 by @Phydra11). It failed with `TypeError: int() ... NoneType` on every retry, for example on an M1 Max with 8-bit paged KV.
- **Flash-Next starts without its draft head again** (#400). `mtplx serve --generation-mode ar --no-load-mtp`, and `--stock-ar`, refused to load Flash-Next with "relaxed Qwen4 draft ties require native MTP" (an M1 Ultra in #400). Plain decoding is the fallback on Macs where speculative decoding runs slower than plain decoding.
- **A server at Metal's buffer limit keeps serving** (#640). After about two days on an Ultra every request failed with `Resource limit (499000) exceeded` until a restart, because the memory guard freed bytes and the limit counts buffers. The guard now releases the saved state of idle conversations, oldest and SSD-saved first, and the 507 says it is a buffer count, not memory, and that a restart recovers it if nothing idle was left. What still holds the buffers on those Ultras is not found yet (see Known issues).

### Claude Code

- **Each conversation keeps its session through compaction, and each subagent gets its own** (#606 by @jvmenen). MTPLX now reads Claude Code's session header. Subagents shared the parent's session and got 409 "already in flight"; a subagent now runs in its own session, and a second request on a busy Claude Code session runs beside it instead of failing.
- **Side requests no longer replace the conversation's cached turn.** Claude Code sends its session id on the session title, the auto-mode safety check and the command-prefix check too. A request that does not share the conversation's first 4,096 tokens is treated as a side request and finds its own cache. With `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` (Claude Code 2.1.273 and later), MTPLX reads the request class Claude Code sends instead.
- **`/effort` is applied** (#634 by @goodbadwolf). Claude Code's effort level was ignored. `/effort low` and `medium` now run at those levels, and `max` runs at xhigh. `high`, which Claude Code sends unless you pick another level, keeps the server's default (medium on Qwen 3.8 27B and Bonsai 2, xhigh on Flash-Next), so default Claude Code turns think as long as they did in 2.12.2.
- **The auto-mode safety classifier runs without thinking** (#670 by @phaedrus1992, for #669). It asks for a verdict on every tool call and sends no thinking field, which on Anthropic's API means no thinking. Only Claude Code's exact classifier request is matched: its billing block, its system prompt's first sentence, no tools, no streaming and no thinking choice.

### Codex

- **Codex desktop 26.1016 and its bundled CLI can send messages again** (#658). Every turn was refused with a 400 because of `reasoning_summary_delivery`.
- **A preamble and the tool call after it are one assistant turn** (#603). Codex sends a short preamble ("Reading the importer first:") as its own message before the call. MTPLX made two assistant turns of it, and after 10 to 25 tool calls the model copied the pattern and stopped without a call, which Codex reads as the end of the task.
- **Codex keeps waiting while MTPLX reads a long prompt** (#680 by @SuperMarioYL). The Responses stream sent nothing between its first status event and the first token, so on a long cold prompt Codex's idle timer could end the turn before the answer started. MTPLX now sends a status event every 5 seconds until the first token.

### OpenCode and other agents

- **OpenCode 2.x titles no longer stall your turn or throw away its cache.** OpenCode Desktop 2.2 rewrote the prompt it uses to name a conversation and sends it beside every turn, under the conversation's own id. MTPLX no longer recognised it, so the title ran on the model: when it reached the conversation first, your turn was refused with "already in flight" and retried, and the title replaced the conversation's saved state, so the retry read the conversation again (7 s to the first token instead of 0.2 to 0.6 s in a session on November 3, where 8 of 9 refused OpenCode requests were titles). MTPLX now answers OpenCode's title requests at once without the model, titled from the conversation's first message so the title stays put. MTPLX's OpenCode plugin also passes OpenCode's own request kind, so a title is recognised from the first turn of a new conversation.
- **Long OpenCode 2.x answers are no longer cut at 32,000 tokens.** OpenCode 2.x sends its 32,000-token default with every request and no longer lets MTPLX's plugin remove it, so a long answer at xhigh stopped at 32,000 tokens. The server now drops exactly that default for OpenCode requests, as the plugin did; an answer cap you set with `--max-response-tokens` still applies.
- **MTPLX's OpenCode plugin works with OpenCode 2.x from the app too.** OpenCode 2.x runs only a plugin's 2.x entry, which the app's plugin did not have, so under OpenCode Desktop 2.x the app's plugin did nothing. The app now installs the same plugin package as `mtplx`.
- **Clients that read the reply as text can keep tool-call markup** (#674, #675 by @energypantry). On a request without tools, MTPLX replaces `<tool_call>` markup with a notice, which is right for the app's chat and wrong for a client with its own text protocol, where the markup is the command. The server's operator can turn the replacement off with `MTPLX_KEEP_ORPHAN_TOOL_MARKUP=on`, and a client can turn it off for its own requests with an `x-mtplx-keep-tool-markup: on` header or a `"keep_orphan_tool_markup": true` field. Measured by @energypantry on an M3 Ultra with Qwen 3.8 27B (a 34-file refactor over a plain-text protocol): 36 turns and 452 s instead of 40 turns (the limit) and 577 to 696 s, and 1 eaten command instead of 7.
- **The tool-call example shows how parameters are written** (#584). In OpenCode's compact tool mode the example call is the only place the prompt shows a call, and it was built from the first tool, which in the report takes no parameters. After a screenshot the model then wrote arguments as `"<parameter=290>"`. The example now uses the first tool that has parameters, and is unchanged when the first tool has them. It has not yet been run with the reporter's script on a model.
- **An answer that ends inside an unclosed reasoning block is returned** (#583, #588 by @jvmenen). With tools declared it came back empty. It is now returned as the answer when the turn stopped naturally and holds no tool call.

### The app

- **The Settings popover, the launch overlay and the model picker open in one step.** They opened in a stagger of about one second and now open in a single 0.2 s step, or at once with reduced motion. On an M5 Max, in the 1.5 s after a click on Settings, the app used 550 ms of CPU instead of 881 ms and WindowServer 322 ms instead of 512 ms (median of six opens per version, the two versions taking turns). A slider you drag keeps its own value until you let go, then sends one change to the engine.
- **The app asks the engine for less while it answers.** During any request, from Pi, OpenCode or the app's own chat, the app asks for a dashboard snapshot every 500 ms instead of every 100 ms, and once a second when its window is closed or out of sight. The live gauge still moves 10 times a second, and a slower cadence you chose in Settings is kept.
- **The app's gauge no longer costs a CPU core while the engine answers.** The gauge's speed number and its glow were redrawn on the CPU for every frame of every digit change, for as long as the engine answered. They are now drawn on the GPU. On an M5 Max during a Flash-Next answer, with the Live tab showing, the app used 0.22 of a CPU core instead of 1.22 (216 against 1,215 ms of CPU a second). With the window closed it uses 0.004 of a core. The gauge looks the same.
- **The Live tab says when macOS slows the GPU because of heat.** The notice shows while macOS reports heavy thermal pressure and clears when it eases, in all 13 languages.

### Dashboard and request log

- **The request log says what really happened to a request** (#652, #631, #600, #617 by @jvmenen). A request cancelled during decode keeps its real cache outcome instead of a miss; a request that found nothing to reuse says why (a new chat, no shared prefix, an evicted entry) instead of blaming the SSD cache; a 507 or 503 shows as a refusal, with its reason and when a retry can work; and the flight log and dashboard show how long a request waited for other work before its own started.
- **The dashboard's Cache tab shows what RAM and the SSD hold** (#622), **the decode chart plots live samples over the whole five minutes and shows the value under the cursor** (#598, #626), **and the verify waterfall is readable** (#590), by @jvmenen.

### Other fixes

- **Paste or drop images into the web chat** (#601). The chat at the server's root page now sends a pasted screenshot or a dropped image file with your message when the model can read images, shows each one as a thumbnail you can remove, and says so when the model reads text only.
- **`--scheduler-mode mtp_batch` says once which models it serves.** It is a mode for the Qwen 3.6 35B-A3B packs. On Flash-Next its error asked for `--verify-strategy target_prefix`, which Flash-Next then replaced, so the same error came back whatever you set (a report on the Flash-Next model page). It now says the mode serves the 35B-A3B packs only and which flags to drop.
- **DeepSeek MTP packs skip the output head when only the last row or no logits are needed** (#636 by @sypsyp97).
- **The opt-in incremental SSD encode tells a block with flipped signs from the old one** (#596 by @jvmenen).
- **Structured output says why it is refused** (#643). With llguidance installed but unable to load (1.3.0 in the report), every `json_schema` request said "pip install llguidance", which pip answers with "Requirement already satisfied". The refusal and `mtplx doctor` now name the installed version, the error, the 1.8 minimum and the pip command for the Python MTPLX runs on.
- **Fan watchdogs exit when their fan lease ends** (#602). In smart fan mode each ramp started a watchdog process that stayed alive until the server stopped.
- **`mtplx forge build` works with a relative `--out`** (#627, found and diagnosed by @Starefossen). The contract probe wrote its result one folder too deep and calibration failed with agreement 0.0.
- **Gemma 4 loaded without its draft model runs** (#632 by @jvmenen). Its first forward pass failed with `unexpected keyword argument 'shared_kv'`.
- **`lock_wait_time_s` in the request log includes the time a request waited behind another** (#576 by @jvmenen).
- **The test suite ignores the shell's `MTPLX_` settings and never opens the real session cache** (#644 by @jvmenen).

### Added

- **`--trust-network` serves without an API key on a network you trust** (#491). A server bound beyond localhost still refuses to start without a key by default. `--no-auth --trust-network` together serve without one, and the startup banner says that anyone who can reach the port can use the model.

## Known issues

- **Flash-Next on Ultras can still reach Metal's buffer limit after long uptime** (#640). The engine now recovers by releasing idle conversations, but what holds the buffers there is not found. On single-die Macs (M3, M4, M5 Pro and Max), each compiled verify re-trace with the hyper-connection read leaves about 9 Metal buffers and about 380 graph nodes inside MLX (#546). A re-trace happens about once per 8,000 tokens of growth past 16,000 tokens, and on every turn below that. A restart returns them.
- **OpenCode re-reads part of its prompt at each new turn when your home folder holds the same skill twice.** OpenCode lists the skills it finds under `~/.claude/skills` and `~/.agents/skills` in its system prompt, and each new `opencode run` picks between duplicate copies differently, so the prompt changes a few thousand tokens in. Keeping one copy of each skill keeps the prompt stable. Tool loops inside a turn are not affected.
- **Flash-Next with plain decoding and its draft head still loaded reads the whole conversation again on every turn.** This is `--generation-mode ar` or `--no-mtp` without `--no-load-mtp`, or the app set to plain decoding with the draft head left on. Add `--no-load-mtp`, which also frees the draft head's memory. 2.12.2 behaved the same.
- **Kilo loses track of tasks after a compaction** (#653) has the same shape as #635 and may be fixed by it; it was not reproduced.
- **On models other than Flash-Next, with the SSD cache off, a plain API chat resumes from its first turn's prompt instead of the previous turn's.** The re-read grows by one reply per turn, as in 2.12.2. Saving that prompt would copy the conversation's cache on those models; keeping the SSD cache on (the default) avoids it.
- **Structured output needs the `server` extra.** Homebrew and plain `pip install mtplx` do not install llguidance; the refusal now gives the command.
- **The known issues of 2.12.2 still apply.** See the [2.12.2 release notes](https://github.com/youssofal/MTPLX/releases/tag/v2.12.2).

## Upgrading

Run `brew upgrade mtplx` or `pip install -U mtplx`, or use the app's update check. You don't need to change any settings. The first turn of each Flash-Next conversation saved by an earlier version reads its prompt once.
