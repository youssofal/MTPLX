The substitution mechanism in `rafale/draft/ramp.py` relies on a specific, somewhat accidental, property of the MTPLX engine's import architecture: **function-local imports**.

In `mtplx/generation.py`, the `generate_mtpk` function does not import the context-copy drafting symbols (`NgramIndex`, `block_for_ext`, `context_copy_block_k`) at the module top level. Instead, it imports them inside the function body, which means the import statement is executed on **every single call** to `generate_mtpk`.

This behavior is load-bearing because it creates a "live" binding. If the engine used standard top-level imports, the symbols would be resolved once at startup and cached in the module's namespace. Rebinding `mtplx.context_copy.NgramIndex` after the engine module had already been imported would have no effect on `generate_mtpk`, because `generate_mtpk` would still hold a reference to the original class object resolved at startup. However, because the import happens inside the function, `generate_mtpk` looks up the current value of `mtplx.context_copy.NgramIndex` in the `mtplx.context_copy` module namespace at runtime, every time. Therefore, if `rafale.draft.ramp.install()` rebinds those attributes on the `mtplx.context_copy` module object before the server starts serving requests, the engine will transparently use the RAMP-provided classes and functions without any source code changes to the engine itself. This is the "no-diff seam."

### Why `install()` Subclasses Instead of Replacing

The `install()` function does not simply replace `mtplx.context_copy.NgramIndex` with a pure-Python reimplementation (like `RampIndex` or `_ExactIndex` defined in `ramp.py`). Instead, it defines a new class `_InstalledRampIndex` that **subclasses** the real engine's `NgramIndex`.

This design choice is driven by the project's prime directive: *"Do not sacrifice the behavior already proven to work."*

1.  **Exact Hit Fidelity:** The engine's `NgramIndex` has been battle-tested in production. By subclassing it, `_InstalledRampIndex` inherits the engine's exact matching logic for the "happy path" (exact n-gram matches). The `find()` method in `_InstalledRampIndex` calls `super().find()` first. If the engine finds a match, it returns that result immediately. This guarantees that for all cases where the stock engine works, RAMP behaves identically to the stock engine.
2.  **Isolation of New Logic:** The only new logic introduced is the "fuzzy fallback" for when the exact match fails. By keeping the exact match path in the parent class, the risk of introducing subtle bugs into the core matching algorithm is minimized. The pure-Python `RampIndex` class exists primarily for unit testing off-Mac (where `mtplx` is not installed) and to provide a reference implementation for the "reduces exactly to the engine's algorithm" control scenario, but it is not used in the live serving path.

### The Block Length and Cap Rebinding

The engine determines the length of the speculative block (how many tokens to propose) using a function `block_for_ext(ext, k_cap)`. This function uses a "ladder" of block lengths (8, 12, 16, 24, 32) based on the backward-match extension length (`ext`). However, the result is capped by `k_cap`, which is derived from `context_copy_block_k()`.

If you wanted to use a fixed, longer block length (e.g., 48 tokens, as recommended by the POC findings for bus-bound machines), simply rebinding `block_for_ext` to return 48 would not be sufficient. The engine calls `block_for_ext(ext, context_copy_block_k())`. If `context_copy_block_k()` still returns the stock default (e.g., 24), the engine's internal logic or the `min()` operation inside the original `block_for_ext` (or its callers) might clamp the result back down to 24.

Therefore, `install()` must **also** rebind `mtplx.context_copy.context_copy_block_k` to return a value at least as large as the desired fixed block length. In the code, if `block` is set, `install()` defines `_installed_block_k` to return `max(4, block)`. This ensures that the cap does not silently truncate the longer block length that the new `block_for_ext` is trying to propose. Failing to rebind the cap would result in the engine using the shorter, stock block length, negating the performance gains of the RAMP proposer.

### Fragility Against Engine Upgrades

This arrangement is inherently fragile against engine upgrades for several reasons:

1.  **Import Location Change:** If a future version of MTPLX moves the imports in `generate_mtpk` from function-local to module-top-level, the "live binding" property disappears. The engine would cache the original `NgramIndex` at startup, and `install()`'s rebinding would have no effect. The RAMP proposer would silently fail to install, and the engine would run with stock behavior. This would be a silent failure, as the server would still start and serve requests, just without the RAMP optimizations.
2.  **API Changes:** If the engine changes the signature of `NgramIndex.__init__`, `sync`, or `find`, or if it changes the return type of `find` (e.g., from a tuple to a dataclass), the `_InstalledRampIndex` subclass would break. Since it subclasses the engine's class, it is tightly coupled to the engine's internal implementation details.
3.  **Block Cap Logic:** If the engine changes how `context_copy_block_k` is used or introduces new capping logic elsewhere, the simple rebinding of `context_copy_block_k` might no longer be sufficient to enforce the desired block length.
4.  **No Verification:** The `install()` function prints a confirmation message, but it does not verify that the rebinding actually took effect in the way intended. If the engine's import mechanism changes, there is no automatic check to alert the user that RAMP is not active. The user would have to manually inspect the engine's behavior or add their own checks.

In summary, the RAMP proposer exploits a specific, non-standard import pattern in the current MTPLX version to achieve a "monkey-patch" style substitution without modifying engine source. This is powerful but brittle, relying on the engine maintaining its function-local import behavior and stable internal API.
