The substitution mechanism in `rafale/draft/ramp.py` relies on a specific, somewhat accidental, property of the MTPLX engine's import architecture: **function-local imports**.

In `mtplx/generation.py`, the `generate_mtpk` function does not import the context-copy drafting symbols (`NgramIndex`, `block_for_ext`, `context_copy_block_k`) at the module top level. Instead, it imports them inside the function body, which means the import statement is executed on **every single call** to `generate_mtpk`.

This behavior is load-bearing because it creates a "live" binding. If the engine used standard top-level imports, the symbols would be resolved once at startup and cached in the module's namespace. Rebinding `mtplx.context_copy.NgramIndex` after startup would have no effect on the already-imported references in `generation.py`. However, because the import happens inside the function, every time the engine needs to instantiate a drafter or calculate a block size, it looks up the current value of `mtplx.context_copy.NgramIndex`. By rebinding these attributes in the `mtplx.context_copy` module namespace before the server starts serving requests, `install()` effectively swaps out the implementation for every subsequent decode step without modifying a single line of engine source code. This is a "no-diff" seam: the engine code remains pristine, but its behavior is altered by changing what its imports resolve to at runtime.

### Why Subclass Instead of Replace?

`install()` does not replace the engine's `NgramIndex` with a pure-Python reimplementation (like the `RampIndex` class defined in the same file). Instead, it defines a new class, `_InstalledRampIndex`, that **subclasses** the real engine's `NgramIndex`.

This design choice is driven by the project's prime directive: *"Do not sacrifice the behavior already proven to work."*

1.  **Exact Hit Fidelity:** The engine's `NgramIndex` has been battle-tested for exact-match context copying. By subclassing it, `install()` ensures that whenever an exact match is found, the behavior is **identical** to the stock engine. The `find` method in the subclass calls `super().find()` first. If the engine finds a match, it returns immediately, preserving the engine's exact logic, edge case handling, and performance characteristics for the common case.
2.  **Isolation of New Logic:** The only new logic introduced is the **fuzzy fallback**. This logic only executes if `super().find()` returns `None` (a miss). This strictly separates the "proven" path (exact match) from the "experimental" path (fuzzy match). If the pure-Python `RampIndex` were used instead, any subtle difference in how the pure-Python version handles exact matches (e.g., tie-breaking, candidate ordering, or memory layout) could silently alter the output or acceptance rate, violating the quality gate. Subclassing guarantees that the "control" scenario (RAMP disabled or exact hit) is byte-for-byte identical to the baseline.

### The Block Length and Cap Trap

The engine determines the length of the speculative block (how many tokens to propose) using a function `block_for_ext(ext, k_cap)`. This function takes two arguments:
*   `ext`: The length of the backward match extension (a signal of confidence).
*   `k_cap`: A hard cap on the block size, derived from `context_copy_block_k()`.

The stock engine has a fixed ladder of block sizes (e.g., 8, 12, 16, 24, 32) and a default cap (often 24). The POC findings showed that for this specific hardware and workload, a **fixed, longer block** (e.g., 48) outperforms the adaptive ladder.

If `install()` simply rebound `block_for_ext` to return a fixed 48, it would **fail** if the engine's internal `k_cap` remained at its default (24). The engine's code likely does something like `min(block_for_ext(...), k_cap)`. If `k_cap` is 24, the engine would clamp the proposed 48 down to 24, silently reverting to the suboptimal behavior.

Therefore, `install()` must **also** rebind `context_copy_block_k` to return a value at least as large as the fixed block size (e.g., `max(4, block)`). This ensures that the cap does not silently re-clamp the longer block. This is a critical coupling: changing the block length without adjusting the cap is a silent failure mode that would make the RAMP patch appear to have no effect.

### Fragility Against Engine Upgrades

This arrangement is inherently fragile against engine upgrades for several reasons:

1.  **Import Location Change:** If a future version of MTPLX moves the imports in `generate_mtpk` from function-local to module-top-level, the substitution will **silently stop working**. The engine will use the original `NgramIndex` and `block_for_ext`, and RAMP will have no effect, but no error will be raised. The server will run, but it will run with the stock drafter.
2.  **API Signature Changes:** If the engine changes the signature of `NgramIndex.__init__`, `find`, or `block_for_ext`, the subclass in `install()` will break. For example, if `find` gains a new required keyword argument, the `super().find()` call in `_InstalledRampIndex` will raise a `TypeError`.
3.  **Internal Logic Changes:** If the engine changes how it interprets the return value of `find` or `block_for_ext` (e.g., if `ext` is no longer used for block sizing, or if the cap logic is moved elsewhere), the RAMP patch may produce incorrect results or fail to achieve its intended performance gain.
4.  **Module Structure Changes:** If the engine moves `NgramIndex` or `block_for_ext` to a different module (e.g., `mtplx.drafting` instead of `mtplx.context_copy`), the rebinding in `install()` will target the wrong module, and the engine will continue to use the old symbols.

Because of these fragilities, `install()` is **off by default**. It must be explicitly enabled, and the project relies on the `scripts/launch_ramp_server.sh` script to ensure it is only used in controlled, tested environments. The `RampCounters` returned by `install()` allow the caller to verify that the patch is actually being hit (by checking `probes`, `exact_hits`, `fuzzy_hits`), providing a runtime sanity check that the substitution is active.
